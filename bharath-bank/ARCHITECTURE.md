# Architecture

This document describes the internal design of the Bharath Bank of India
Flask app: the database schema, the request → transaction flow, the
ledger/balance engine, and the money-representation strategy. All details
below are taken directly from `app.py` (`init_db()`, `_post_transaction`,
and the route handlers) and `finance.py`.

## Tech overview

- **Web framework**: Flask, single module `app.py` (no blueprints).
- **Database**: SQLite, accessed with the standard-library `sqlite3`
  module — no ORM. One connection per request context, stored on Flask's
  application-context object `g` (`get_db()` / `close_db()`), with
  `PRAGMA foreign_keys = ON` set on connect.
- **Schema creation**: `init_db()` runs a single `executescript()` with
  `CREATE TABLE IF NOT EXISTS` for every table, then calls
  `seed_reference_data()` to populate the two read-only catalogue tables
  (`schemes`, `loan_products`) if they're empty. This runs once at process
  start (`if __name__ == "__main__": init_db()` before `app.run()`).
- **Financial math**: isolated in `finance.py` as pure functions (no I/O),
  imported into `app.py` as `finance`.

## Database schema

All monetary columns are suffixed `_paise` and store `INTEGER` amounts (see
"Money as integer paise" below). Tables are listed in the order they
appear in `init_db()`.

### Entity relationships

```
users 1──1 customer_profiles
users 1──* accounts
accounts 1──* transactions
users 1──* deposits
users 1──* loans
loans 1──* loan_payments
schemes ···· (referenced by code/name copy, not FK) ···· deposits
loan_products ···· (referenced by code/name copy, not FK) ···· loans
```

`schemes` and `loan_products` are reference/catalogue tables — a deposit
or loan copies the scheme/product's name and rate into its own row at
creation time rather than joining live, so historical deposits/loans keep
the rate that was in effect when they were opened even if the catalogue
changes later.

## Request → transaction flow

A representative write path — **Transfer** (`POST /transfer`) — illustrates
the pattern used across deposit/withdraw/deposits/loans:

1. **Auth gate** — `@login_required` redirects to `/login` if
   `session["user_id"]` is absent.
2. **Look up the acting account** — `get_primary_account(session["user_id"])`.
3. **Validate input** — parse/convert the rupee amount to paise
   (`rupees_to_paise`, rejects non-positive or unparsable amounts) and
   resolve the counterparty account by account number.
4. **Re-read the authoritative balance** at write time (not the value
   loaded earlier in the request) to avoid acting on stale data, and
   reject if funds are insufficient.
5. **Post the ledger entries.** For a transfer this is two calls to
   `_post_transaction()` — a `DEBIT` on the sender and a `CREDIT` on the
   payee — sharing one `ref_no`, with `commit=False` on both so they land
   in the same SQLite transaction, followed by a single `db.commit()`.
   This is the app's **double-entry** guarantee: both legs succeed or (on
   an exception before the commit) neither is durably applied.
6. **Flash a result message** and redirect (POST/redirect/GET pattern) to
   `/dashboard`.

The same shape appears in:
- **Deposit/Withdraw** (`/deposit`, `/withdraw`) — single-leg
  `_post_transaction` call, `commit=True` (the default).
- **Open FD/RD** (`POST /deposits/open`) — debits the savings account for
  the principal/first installment, then inserts a row into `deposits`,
  both under one commit.
- **Pay RD installment** (`POST /deposits/<id>/pay`) — debits the
  installment amount and increments `installments_paid`.
- **Close deposit** (`POST /deposits/<id>/close`) — credits either the
  full projected `maturity_paise` (if past `maturity_date`) or just the
  principal paid in so far (if closed early, no interest), and updates
  `status` to `MATURED` or `CLOSED`.
- **Apply for loan** (`POST /loans/apply`) — computes eligibility, and if
  approved, credits the account with the principal and (if non-zero)
  debits the processing fee — two ledger entries sharing the loan's
  ref pattern — then inserts the `loans` row.
- **Pay EMI** (`POST /loans/<id>/pay`) — computes the interest/principal
  split against the *current* `outstanding_paise` via
  `finance.emi_split`, debits the account, inserts a `loan_payments` row,
  and updates the loan's `outstanding_paise` / `emis_paid` / `status`
  (flips to `CLOSED` once `outstanding_paise` reaches zero).

## How `_post_transaction` keeps a running balance

```python
def _post_transaction(account_id, txn_type, amount_paise, category, description,
                       counterparty, ref=None, commit=True):
    db = get_db()
    row = db.execute("SELECT balance_paise FROM accounts WHERE id = ?", (account_id,)).fetchone()
    balance = row["balance_paise"]
    balance = balance + amount_paise if txn_type == "CREDIT" else balance - amount_paise

    db.execute("UPDATE accounts SET balance_paise = ? WHERE id = ?", (balance, account_id))
    db.execute(
        "INSERT INTO transactions (account_id, txn_type, amount_paise, balance_paise,"
        " category, description, counterparty, ref_no, created_at)"
        " VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)",
        (account_id, txn_type, amount_paise, balance, category, description,
         counterparty, ref or gen_ref_no(), now_str()),
    )
    if commit:
        db.commit()
    return balance
```

This is the single choke point through which every balance-changing
operation in the app flows. Its design guarantees:

- **One source of truth for the balance.** `accounts.balance_paise` is
  never computed by summing `transactions` — it's a maintained running
  total, updated in the same statement group as the ledger insert.
- **Every transaction row is self-describing.** Each `transactions` row
  stores `balance_paise` as it stood *immediately after* that entry, so
  the full account history (and the running balance at any point in time)
  can be reconstructed by reading `transactions` alone, without touching
  `accounts` or replaying arithmetic.
- **Callers control the commit boundary.** `commit=False` lets a caller
  chain multiple `_post_transaction` calls (e.g. both legs of a transfer,
  or a loan disbursal + fee) and commit them together as one atomic
  SQLite transaction — either both ledger rows and the balance update all
  land, or (if an exception occurs first) none of them do.
- **Balances are re-read, not trusted from earlier in the request.**
  Route handlers re-query `balance_paise` right before validating
  sufficiency (see `withdraw`, `transfer`, `pay_rd`, `pay_emi`) rather than
  reusing a value fetched at the top of the request, reducing the window
  for a stale-balance bug within a single request/connection.

## Money as integer paise (avoiding float drift)

Every monetary column in the schema is an `INTEGER` counted in **paise**
(1 rupee = 100 paise), never a `REAL`/float rupee amount:

- **Input boundary**: `rupees_to_paise()` takes the rupee string typed
  into a form, does the *only* float arithmetic on user-facing money
  (`float(value) * 100`), and immediately rounds and casts to `int` —
  after this point in the code, the value is a plain integer.
- **Storage & arithmetic**: `_post_transaction` and every route add/
  subtract these integers directly (`balance + amount_paise`) — this is
  exact integer arithmetic, so repeated deposits/withdrawals/transfers can
  never accumulate the rounding error that plain IEEE-754 floats would
  introduce over many additions of fractional rupee amounts.
- **Financial formulas still use floats internally** (`finance.py` uses
  `float` growth factors like `(1 + r/400) ** quarters` because compound
  interest and EMI formulas are inherently non-integer), **but every
  function's boundary rounds back to an integer number of paise**
  (`int(round(...))`) before the value re-enters the ledger — so floating
  point only ever exists transiently inside a single calculation, never
  persisted or accumulated across transactions.
- **Output boundary**: `fmt_inr()` converts the integer paise back to a
  human-readable, Indian-grouped rupee string (e.g. `1234567` paise →
  `₹12,345.67`) purely for display, via integer division/modulo
  (`paise // 100`, `paise % 100`), not float division — so display
  formatting also can't introduce drift.

The net effect: the only floating-point numbers that ever exist in this
app are short-lived intermediate growth factors inside `finance.py`, and
the once-per-input conversion in `rupees_to_paise`. Every value that is
actually stored, summed across transactions, or compared for
sufficiency-of-funds is an exact Python `int`.
